## 2. How the holdout is reached

**One switch, in one place.** Three things differ on the phase-E side and nothing else does:
the file the setup chain starts from, the backtest scheme it is evaluated under, and the span
the province and training-window forks call "evaluated". Six setup scripts and `conclude.py`
needed all three, and all three are now answered by
`analysis/scripts/lib/combos.py`, from the `__holdout` suffix batch 15 froze the manifest's
row names with.

This is the same lesson six defects have taught this project — batch 14 found four counts of
one step discovering something the tree already knew, and batch 22 two more — applied here
before there was a defect to find. The reason is the same: a holdout row must run
*the same analysis* as its development twin, and the way to make that checkable rather than
asserted is for there to be one place the difference lives. Deriving the phase from the
combination name also means the driver sets one variable — `COMBO` — exactly as it does for
every other row, so there is no second switch to set inconsistently with it.

**Every development setup spec was re-derived and moved only in the fields it gained.**
`evaluated_on`, `source_dataset`, `identical_to_source_dataset` and a scheme key on each
`eval_flags_source` entry. `dataset_sha256`, `eval_flags`, row counts and locations are
unchanged in all twelve. Nothing numeric in the tree moved.

## 3. Opening the seal

`01_data/01_partition` gained `open_holdout.py`. It puts the development file and the sealed
file back together **in the archived source's own line order** and verifies the result is
byte-identical to that source. Nothing is re-derived from the raw data; the assembly is on
lines and the verification is on hashes, so no case value of 2010 is parsed by the script
that opens the year.

**Why a third file rather than pointing `02_setup` at `Archive/`.** Two reasons and neither
is tidiness. The archive is `(IS_SHADOW)` material with its own checksum manifest, and a
setup stage reaching into it would put the read outside the tree where no node's provenance
covers it. And the licence to read the whole record belongs to this node *because* this is
where the proof lives that the two parts partition the source exactly — which is the fact
that makes putting them back together legitimate rather than a second import of the data.

**The evidence that the set predates the opening** is that `manifest_holdout.csv` was added
at `937fd5c` and the first file under `analysis/results/*__holdout/` appears at `895a9f8`.

## 6. What went wrong, kept

**The driver began re-running `main__holdout`.** The first invocation over the whole manifest
had no reason to skip a row that had already run, and the reference is unseeded, so a second
pass would have replaced the denominator of every number already reported with a different
draw. It was stopped at the persistence baseline — the reference was never reached — and
those files were restored from the previous commit. The fix is in the driver: it reads
`run_status_holdout.csv` and refuses to run a row it already records. From a clean checkout
there is no such file and the whole set runs, so `analysis/run.sh` still reproduces phase E
from nothing. This is plan §3's second half turned from an instruction into code.

**`freeze_holdout_manifest.py` was overwriting its own evidence.** `frozen_at_commit`
recorded HEAD at write time, so running the script again after the holdout turned batch 15's
`f3904c5` into batch 16's own commit. It now reads the commit that *adds*
`manifest_holdout.csv` — `937fd5c` — from `git log --diff-filter=A`, which no later run can
overwrite. Editing the script that writes the frozen manifest was only safe because the
manifest itself comes back byte-identical after the whole set has run; that was checked
before the change and again after.

**A number was sitting in a figure title.** `fig_fork_sensitivity.py` said "Six of seventeen
judgment calls move the conclusion" in a string. It is now counted from the bars, which it had
to be for the figure to say the right thing on the second dataset — and which it should have
been anyway, because a number nothing computes is the transcription `AGENTS.md` §1 is about.

**The root node's `claim.md` had been stale since batch 7.** Its answers still said the
project had no candidate model and that a baseline was standing in for one, and its child
list named only `01_data`. Both are rewritten. Nothing else read them, which is exactly why
they went nine batches without being noticed.

## 7. What this batch did *not* do

**It built no `06_holdout` node**, although `analysis/README.md` had reserved one. The
holdout is not a second question: it is the stability question asked of a second year, over
the identical set of analyses, against the identical yardstick, with the frozen manifest and
the freeze record already at `05_stability`. A node whose claim restated that node's and whose
scripts were that node's under other names would make the tree larger and not clearer. The
headline holdout number is where the headline development number is — at the root, written by
the same `conclude.py`, in `analysis/results/main__holdout/conclusion.json`.

**It changed nothing about the analysis after seeing a holdout number.** No row was added,
dropped, re-tuned or re-run. The one thing that moved after the numbers were in is the
driver's own guard against re-running, and it can only reduce what runs.

**It did not close the per-split diagnostics gap** batch 22 opened and batches 14 and 15
declined to close. Batch 15 noted it could still be closed on the holdout side; doing so would
have meant adding work to the holdout half that the development half does not have, which is
the asymmetry the frozen pairing exists to prevent. It stays open, permanently, on both.

## 10. What is still unknown

- **Whether `analysis/run.sh` reproduces this from cold.** It is now about six hours and has
  never been run end to end from a clean environment. `/validate cleanroom` in batch 18 is
  where that gets a number, and it is the single largest untested claim in the repository.
- **Why the reference model improves by 23 % when two silent provinces are removed from what
  it trains on, on 2010, and worsens slightly on development.** The measurement is solid and
  the mechanism is not established. Nothing here may be re-run to find out.
- **Whether the width of the holdout spread is about 2010 or about one-year backtests.** Four
  splits resolve less than eight, and this project has one held-out year. The optional batch
  20 — the same model on `tha` and `vnm` — is the only thing in the plan that would bear on
  it.

## 11. For the human

- **The project has its answer.** The model beats the field's own model and both required
  baselines on a year it had never seen, by +0.0868 of skill, and that number is one member
  of a distribution running −0.5038 to +0.2026 over analyses that all looked equally

- **The finding worth the manuscript is not the win.** It is that **the development set was a
  weak guide to the held-out year** — rank correlation +0.396 across the analyses — and that
  **the analysis development ranked highest among those that change the data or the models is
  the one that collapsed hardest**, because the choice behind it moved the model we were being
  compared against rather than the model we built. A system optimising freely against a
  development set would have taken that row.
- **`analysis/run.sh` is now about six hours.** Batch 15 offered to split the stability run
  out of it if you would rather; that offer stands and now covers both halves. The argument
